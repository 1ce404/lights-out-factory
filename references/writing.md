# 写底稿（④）

脚本 agent 自己写，人审，审过的文案交给平台逐字建脚本、每段开 AI 改写出多种说法。写法学的是**团队交付过、客户认可的稿**（`gold/` 和 `sources.recent_scripts`），不是平台自己生成的文案。

```bash
python3 -I scripts/brief_card.py --config $C --run $R              # 当天每个 brief 一张任务卡
python3 -I scripts/brief_card.py --config $C --run $R --brief <id> # 只看一个
```

任务卡列出写这一条要的全部东西：排期这一行、骨架、卖点和机制的固定说法、产品要求、素材画面、禁用词、平台提示词 `video_script_create` 里的文案规则、同产品同方向的范本和团队交付过的稿、审核人改过的句子、已经用过的开头、今天的热梗。照卡写，写完填进 brief 的 `segments`。

> 下面是千川口播带货的默认写法。你们的写法不一样，改这份文档、`brief_card.py` 的骨架和 `gold/`（见 [adapt.md](adapt.md) 第 4 节）。

## 1. 排期这一行就是任务

店铺/产品 × 内容方向 × 测试卖点 × 人群。**方向和人群决定开头，测试卖点决定中间讲什么。** 方向括号里的字和人群是标签，不念出来（`direction_notes` 写团队实际怎么用这个标签）。

## 2. 骨架：5~6 句，每句一个任务

| 句 | 任务 | 每条要新写吗 |
|---|---|---|
| ① 开头 | 戳一个使用者的问题状态（`writing.subject`），或给一个让人停下的说法 | **要**，跟方向和人群走 |
| ② 引产品 | 一句话带出产品全名 | 换个说法就行 |
| ③ 卖点 | 测试卖点，说它做了什么 | 用产品 config 的 `say`，可以复用 |
| ④ 效果 | 用完看得见、摸得到的结果 | 可以复用 |
| ⑤ 机制 + CTA | 节点 + 机制 + 引导下单 | 可以复用 |

团队稿里 ③④⑤ 常常一字不差地用在不同 brief 上，真正每条不同的是 ①（有时连 ②）。所以 lint 只查开头撞车。

- **开头不报机制**：价格、机制、套组、瓶背、成分表不放第一句（`writing.opening_banned_regex`），机制只放最后一句
- **例外**：`writing.opening_deal_ok_directions` 里的方向（默认「爆款复刻」：照着爆款写，爆款就是机制开头）可以机制开头；`opening_never` 里的（瓶背、成分表）还是不行

## 3. 开头

第一句要让观众认出自己的问题，可以带一句场景或热梗当引子，第二句落到问题状态。**场景只点一句**：素材库里没有的画面（见产品 `footage`），写了也接不住。

同一天同产品的几条，**换开头的类型，不只是换个词**。从 `writing.opening_types` 里轮着选，同一类型最多两次：

| 开头类型 | 怎么写 |
|---|---|
| 反问 | 用一个问题戳到问题状态 |
| 判断 | 给一个观点（「选 X 别只看 Y」） |
| 金句 | 一句氛围 / 金句 |
| 场景引子 | 一个生活场景，马上落到问题 |
| 对话 | 跟观众说话（「你先看 A 还是先看 B？」） |
| 热梗 | 见第 8 节 |
| 直戳问题状态 | 直接描述问题的样子 |

不用：绕弯子的问句（「先别急着…」）、技术名词释义、瓶身包装外观。

## 4. 每句写 2~3 个说法

三种语气各一：口语带情绪 / 正常叙述 / 偏书面。主版写在 `text`，另外 1~2 个写在 `alt`（列表）。审核人在待审文档里挑或改；提交时审过的说法写进这条脚本的改写要求，平台改写时在这个范围内换措辞。每个说法 lint 都查。

## 5. 改写时会走样的地方

平台改写会自己加东西。改写要求里默认写死三条（`writing.rewrite_rules`），成片也会查：

- **不加语音指令**：平台会在句首加 `[#用xx的语气]`，几段语气差太多，一条视频听着像两个人。成片里有的不算可交付
- **产品出现后只讲好结果**：不写「过一会儿又…」，读起来像产品没用（`writing.after_use_bad_regex`）
- **不写时间线**：「早上……下午……」很容易被改成前后对比（`writing.timeline_regex`）

所以写稿时问题只放在产品出现之前，产品之后的每句都是用完的好结果。

## 6. 硬性要求（lint 会查）

- 产品全名完整出现、不被标点拆开；尽量第 `name_not_before + 1` 段才出现；第一次讲卖点那句带产品名，不用「这瓶」「这款」代替
- 测试卖点出现（`must_mention`）；机制只用 `allowed_numbers`；结尾有 `cta_required`；节点期间带节点词
- 禁用词、产品 `banned_words` / `warn_words`、时间承诺、极限词、别的产品的卖点（`foreign_claims`）
- 一个短句一条字幕：显示宽度 > `clause_hard_max` 报错，> `clause_warn_max` 提醒；整条字数在 `combo_chars_min`~`combo_chars_max`
- 开头不撞：开头两句和范本 / 近 `history_days` 天同产品 / 当天其它稿相似度 > `opening_similar_max`，或同一天第一句开头 4 个字一样，报错；同一天另一个业务的第一句太像也报错
- 画面：分段的 `visual_tags` 只能从 `footage_tags` 里挑；讲成分 / 技术的句子配 `ingredient_footage`

lint 不查文风，文风靠人审。

## 7. 每句配什么画面

平台建脚本时给每段挑一个素材标签，常常对不上这句话（讲使用的句子配到了产品外观）。写完逐句对一遍：这句该看到什么。对不上的在分段里写 `visual_tags`（从 `footage_tags` 挑，写两个任一命中；素材少的标签配一个素材多的兜底）。`submit` 建脚本时按它改。

## 8. 热梗（用户要的时候才加）

写稿前查热梗，写进 `$R/hotspots.json`，每个梗指定用在哪几个 brief，任务卡会列出来：

```json
[{"topic": "梗", "since": "2026-10", "meaning": "什么意思", "source": "新华网 2026-10-20", "url": "https://…", "briefs": ["1120-B02"]}]
```

- 来源：抖音热点宝 / 巨量算数（最准）、官方热榜和热榜聚合、新闻报道、年度流行语榜。**不用梗百科**这类只算站内搜索的榜
- 每个梗至少一个来源，写清 `since`；只在梗词典里查得到的不用
- 能一句话转到问题状态的才用；不挑灾难事故、社会负面、政治、明星个人、别的品牌
- 一个 brief 最多一个梗，只放开头一句；找不到够格的就不加

## 附：brief 格式

`parse_schedule.py` 生成空壳，agent 填 `segments`：

```json
{
  "brief_id": "1120-B01", "product_key": "degreaser",
  "direction": "解决问题", "selling_point": "泡沫去油", "audience": "宝妈", "quantity": 10,
  "segments": [
    {"id": 1, "role": "hook", "title": "开头", "text": "灶台边那圈黄黄的油，抹布越擦越黏？",
     "alt": ["灶台那圈油，你是不是擦得胳膊都酸了？"], "visual_tags": ["油污特写"]},
    {"id": 5, "role": "cta", "title": "机制", "text": "现在拍一发二，进直播间带走！"}
  ]
}
```

`role`：`hook` / `pain` / `product` / `selling` / `effect` / `cta`，第一段 `hook`，最后一段 `cta`。用户给了结构就照结构分段，填 `template`。
